# 税務検証データ（fixtures）の合成化・移行方針案

> 作成: 2026-07-25。**方針案であり未実装**。
> **優先度: 低**（`fixtures/` は本リポジトリに未流入と確認済み。実データを持つ別環境の
> 可視性・保管・破棄はリポジトリ所有者が管理する）。本リポジトリで実際に効くのは
> **§4 の予防措置**のみで、そこだけ先に入れることを推奨する。§2 の合成ジェネレータは
> 未観測ケース（ショート建玉・部分決済・CANCELED crypto 出庫・丸め境界・BTC 建て）の
> テスト手段として、実データ管理とは独立に価値があるため P1 として残す。
> 関連: [tax-requirements.md](tax-requirements.md) §8（テスト計画）・§9-8（未観測形状）、
> [tax-research.md](tax-research.md) 付録E、[tax-p0-design.md](tax-p0-design.md) §4-1。

## 0. 前提の確認（重要）

**`fixtures/` は本リポジトリには存在しない** — 作業ツリー・全ブランチ・git 履歴（追加履歴ゼロ）
いずれにも無い。実データは実機確認と付録E の検証を行った**別環境**にある。

したがって本方針は次の 2 つを分けて扱う:

- **(i) 本リポジトリ**: 実データは未流入。必要なのは**流入を防ぐ予防措置**と、合成データへの置換
- **(ii) 実データを持つ環境**: そちらの可視性・保管・破棄の管理。本リポジトリからは検証できない

## 1. なぜ移行するか

`fixtures/raw/` は識別子のみマスクされ、**金額・日時・銘柄は実データ**である。これは
特定個人の 6 年分の取引・資産プロファイルに相当し、次の性質を持つ:

- 断片ではなく**系列**なので、取引パターン・保有推移・積立の有無・付与の受領歴まで復元できる
- 匿名化が困難: 金額と時刻の組は、取引所側の板情報や他データセットと突合すれば同定に近づく
- 一方、**テストに必要なのは「構造的性質」だけ**であり、実際の金額・日時・銘柄である必要はない

## 2. 合成 fixture ジェネレータの設計案（P1）

### 2.1 基本方針

- **決定論的**（seed 固定）。同一 seed → 同一出力。`gen-ratio-reference.py` と同じ思想
- **出力は API の生レスポンス形状そのまま**（`{"success":1,"data":{"trades":[...]}}`）。
  既存インポータを一切変更せず通せる
- **プロファイル駆動**: 件数・分布をデータで宣言し、コードは分布に従うだけ
  （`small-retail` / `vip-scale`(10^5 件) / `margin-heavy` / `edge-cases`）
- **生成時に不変条件を保証する**: 生成した約定・入出庫列から理論残高を再構築し、
  同時に出力する `assets` fixture と**必ず一致させる**。手書きフィクスチャでは作れない性質で、
  残高突合（ガード(d)）のテストが成立する前提になる

### 2.2 再現すべき構造的性質（実データから統計だけ抽出し、値は捨てる）

| 分類 | 再現する性質 | 根拠 |
|---|---|---|
| ペア | JPY 建て中心 + delist 済みペアの混在 + 過年度の BTC 建て | 実機#4・付録E.5 |
| 約定 | 件数規模、pair ごとの偏り、maker/taker 比、負手数料の出現率 | 実機#3 |
| 手数料 | quote 側は 4 桁丸め、base 側は 0、`fee_amount_quote == fee_occurred_amount_quote`（現物） | 付録E.1 |
| 時刻 | **同一ミリ秒の重複**（ページ境界で重複が返る）、JST/UTC 年境界をまたぐ約定、時間帯の偏り | 要求仕様 §2.1 |
| 数量 | 8 桁、pair の `amount_digits` に依存した刻み | 付録E.3 |
| 入出庫 | crypto/fiat の 2 系統、`txid=null`、円未満端数、`CANCELED` | 付録E.3 |
| 信用 | `position_side`、建て時は `fee_amount_quote=0` で `fee_occurred` のみ、決済時に累計精算、`interest` は 0 時またぎ回数 × 0.04% | 実機#2 |
| 残高 | ダスト残差（入庫の小数桁 > pair の `amount_digits`） | 付録E.3 |

### 2.3 生成すべき未観測ケース（実データに存在せず、実口座では作れない）

ここが合成化の**最大の利得**である。実データ回帰では永久に埋まらない穴を塞げる。

| ケース | なぜ必要か |
|---|---|
| **ショート建玉**（`position_side: short`）と決済 | 実データは long のみ。売建ての金利・品貸料の符号が逆（v2 §5） |
| **部分決済** | 建玉を複数回に分けて決済 → 数量按分・金利按分の規則（v2 §5）が未検証 |
| **fiat 入庫行**の全パターン | 実データは行数が少なく、通常入金と付与痕跡の識別境界が薄い |
| **`CANCELED` の crypto 出庫** | 実データは fiat のみ。除外ロジック（要求仕様 §3.2）が未検証 |
| **互換モードの丸め境界** | 簿価 × 残数量がちょうど整数になる系列を意図的に作る（ADR-005 の核心） |
| **BTC 建て約定（`TRADE_EXCHANGE`）** | 新規注文停止のため実機で作れない（実機#4）。円換算（P-07）と暗号資産建て手数料（P-11）の唯一の検証手段 |
| **全量処分（数量ちょうど 0）** | P-03 の簿価掃き出しの境界 |
| **年またぎ未決済建玉** | 当年損益に含めない（v2 §5）ことの検証 |
| **同一 `trade_id` の重複返却** | 重複排除の検証 |
| **壊れたデータ**（未知フィールド・欠落キー・想定外 enum） | NFR「黙って落ちない」＋保留リストの検証 |
| **10^5 件規模** | NFR の性能テスト、および ADR-005 の分母肥大の実測 |

### 2.4 実データとの同値性の担保

合成データが「実データの代わりになる」ことを示す手順:

1. **プロファイル抽出**（実データを持つ環境で 1 回だけ実行）: 分布パラメータ・件数・比率など
   **統計だけ**を出力する。生値は出さない。出力例:
   `{"pairs": {...出現比率}, "maker_ratio": 0.04, "neg_fee_ratio_in_maker": 0.94, "fee_scale": 4, ...}`
2. その統計をリポジトリにコミットし、ジェネレータの入力にする
3. **移行の受入条件**: 実データで通っていた回帰テスト（付録E の各主張）が、合成データでも
   同じ結論になることを 1 度確認する。確認後は実データをテスト経路から外す

## 3. 移行後の実 fixture の扱い

- **リポジトリには入れない**（本リポジトリは最初から入っていないので、そのまま維持する）
- 残すのは次の 2 つだけ:
  1. **マニフェスト**: ファイル名・SHA-256・レコード件数・取得日のみ（`fixtures/MANIFEST.json` 相当）。
     「どのデータで検証したか」を値を出さずに同定・再現できる
  2. **観測事実の文章**: 付録E のような記述。**値は丸め、丸めた旨を注記する**（今回適用した規律）
- **実データ回帰は opt-in**: 環境変数（例 `BITBANK_TAX_FIXTURES=/path/to/fixtures`）が指す場所に
  実データがあるときだけ実行し、無ければ `skip`。**CI では常に skip**（実データを CI に置かない）
- テストは読み込んだ実 fixture の SHA-256 をマニフェストと照合し、想定外のデータでの
  「通ったつもり」を防ぐ
- **保持の見直し**: 税務検証が完了したら破棄するか、少なくとも年次で保持の必要性を見直す

## 4. 移行までの暫定措置（本リポジトリ）

いずれも小さい変更で、承認後すぐ適用できる。**現状は実データ未流入なので、純粋な予防措置**。

1. **`.gitignore` に先回りで追加**（誤コミットの防止）:
   ```gitignore
   # 実口座データは本リポジトリにコミットしない（docs/dev/tax-fixtures-plan.md）
   fixtures/
   **/fixtures/raw/
   user_spot_trades_archived-*.csv
   *.private.json
   ```
2. **pre-commit で拒否**: lefthook に「上記パスパターンの追加を検出したら失敗」を 1 本追加する。
   `gitleaks` は認証情報向けなので、**パスベースの拒否は別に要る**
3. **可視性**: 本リポジトリは公開フォークで、fork は upstream の可視性に縛られるため
   private 化できないと考えるべき。実データを扱う作業は**別の非公開リポジトリかローカル**に
   限定する（fork の可視性変更を当てにしない）
4. **CONTRIBUTING / README に注意書き**:
   「実口座データ（API 生レスポンス・UI CSV エクスポート）をこのリポジトリにコミットしない。
   検証は別環境で行い、**観測事実のみを丸めて** docs に記載する」
5. **docs 側の規律の明文化**（今回適用済みの規則を規約化）:
   実データ由来の観測を書くときは (a) 値を丸める、(b) 丸めた旨を注記する、
   (c) 恒等式の検算は**値を丸めるのではなく関係式で表す**（丸めると検算が合わなくなり
   証拠価値が失われる）

## 5. 見積りと順序

| 段階 | 内容 | 目安 |
|---|---|---|
| 0 | 暫定措置 1〜5（本リポジトリ） | 30 分 |
| 1 | プロファイル抽出スクリプト（実データ環境で実行・統計のみ出力） | 半日 |
| 2 | ジェネレータ本体（2.2 の構造的性質 + 残高整合の保証） | 1〜2 日 |
| 3 | 未観測ケース（2.3）の生成 | 1 日 |
| 4 | 受入確認（2.4-3）→ 実データをテスト経路から外す | 半日 |

P0（インポータ・突合・エンジン・ガード）は合成 fixture なしでも進められるため、
**本移行は P0 と並行または直後**でよい。ただし段階 0（暫定措置）は**先に入れる**ことを推奨する。
