# 税務・会計データ整形 開発ロードマップ

## 背景と期限

- 取引所側にデータが揃っているのに、税務処理のために利用者が自力でデータを
  組み立て直している（複数ユーザーが独立に指摘）
- **2027 年 2〜3 月の確定申告シーズン（2026 年分）に間に合わせる**
  - 12 月頭までに動くものを完成
  - 11 月中に実データ（年間取引）での検証を終える
  - 7 月下旬起点で残り約 4〜5 ヶ月

## 税制前提（2026 年 7 月時点）

- 金商法・資金決済法等改正法（暗号資産の金商法移管）は **2026-07-15 に成立**。
  暗号資産関連規定は公布から 1 年以内に施行（[tax-research.md](tax-research.md) §12）
- 申告分離課税（20%）の適用開始は「金商法等改正法の施行日の属する年の翌年 1/1 以後の
  譲渡」。2027 年中施行なら 2028-01-01 開始が有力だが、施行日確定までは未確定
- **2027 年 2〜3 月の申告（2026 年分）は現行制度（総合課税・原則その他雑所得）で確定**。
  本ロードマップは現行制度への対応を優先する
- 分離課税は対象が「特定暗号資産」に限定される見込み。対象外の譲渡は
  「総合課税の譲渡所得＋特則」の構造。経路別の具体分類は政省令・通達待ち
- 計算細目の税制調査は **完了**（[tax-research.md](tax-research.md) v2、2026-07-23 受領）。
  反映内容は「税制調査の反映」参照

## ユーザー層

税務ニーズは一様ではない。一つの機能で全員をカバーしようとしない。

| 層 | 特徴 | 必要な整形の深さ |
|---|---|---|
| **A** | 海外 CEX/DEX が主戦場。bitbank は円転の換金窓口 | 正規化まで（損益計算まで行うと他社分と二重計算になるため不要） |
| **B** | bitbank が主戦場（一般〜VIP/MM まで規模の幅） | bitbank 単体の損益計算まで（取得原価・実現損益） |
| **C** | 初心者・ライト層。含み益 20 万円超で心配になる層 | 概算の申告要否の目安＋専門家への誘導（断定的な税務判断はしない） |

## 整形の深さとスコープ境界

1. **生データ出力** — 取引履歴・入出金履歴の CSV/JSON 化（対応する）
2. **正規化** — ペア表記統一・タイムゾーン統一・手数料内訳分離など、
   他社データと合算しやすい共通フォーマット（対応する。A 層の主価値）
3. **損益計算** — bitbank 単体の取得原価計算・実現損益算出（対応する。B 層の核）
4. 他社データとの通算損益計算 — **スコープ外**。正規化データを既存の税務 SaaS
   （Cryptact、Gtax 等）に渡す前提
5. 申告要否・税額の確定判定 — **やらない**。概算の目安と専門家・国税庁への誘導まで

## アーキテクチャ（ADR-004）

```
[共有ロジック層 = CLI 内 tax カテゴリ]（生データ取得 → 正規化 → 損益計算）
        ↓
  A層・B層が実データで CLI Skill を使い倒す
        ↓
  手数料・信用建玉・複数ペア按分などのバグ/仕様漏れが実戦で見つかる
        ↓
  検証済みロジックを MCP Tool が CLI サブプロセス実行で利用
        ↓
  C層は自然言語で対話。Tool 側で計算を完結、LLM は説明・目安・誘導に専念
```

- 損益計算は CLI 内 `tax` カテゴリに実装（ADR-002 の例外。`paper` の前例に倣う）
- Skill は計算しない。CLI コマンドが返す確定値のみを使う（税務は間違えられない領域）
- 課税方式（総合課税/分離課税）は入口パラメータとして最初から持たせる。
  分離課税ロジックの実装は制度詳細確定後（2027 年前半に判断）
- 税務の年区切りは JST。「JST は表示・説明用のみ」規約の例外として
  `cli/date-utils.ts` に JST 年境界ヘルパーを追加する
- tax 出力に免責文言を機械可読な形で含める。C 層 MCP は read-only API キー導線
  （[botter-runbook](../botter-runbook.md) の read-only profile）を前提にする
- private GET とローカル計算のみ。trade エンドポイントには一切触れない

## Week 1 で潰す前提リスク（実機確認）

| # | 確認項目 | NG だった場合の影響 |
|---|---|---|
| 1 | **API 履歴保持期間**: trade_history / deposit_history / withdrawal_history が 2026-01-01 JST まで遡れるか | Web の取引報告書 CSV 取込へのフォールバックが必要（計画への影響が最大） |
| 2 | 信用の金利・建玉管理料が trade_history の `interest` に出るか | 控除項目が API だけで完結せず、段階 3 の仕様変更 |
| 3 | maker リベート（マイナス手数料）の出方（quote/base どちらに乗るか） | 手数料の原価算入仕様に影響 |
| 4 | 非 JPY ペア約定の有無 | 約定時点の円換算ロジックが段階 3 に必須になる |
| 5 | 出金 `fee` が `amount` 込みか別建てか | 正規化スキーマの手数料内訳分離の仕様 |
| 6 | API に存在しない課税イベントの棚卸し（貸暗号資産の利用料、キャンペーン等） | 免責明記 or Web CSV 取込のスコープ判断（Week 4 までに決定） |

### 実機確認の結果

- **#1 履歴保持期間（2026-07-22 確認・クリア）**: trade_history は **5 年以上前**の約定まで
  遡及可（5 年スパンの since/end 指定も受理）。deposit_history も同時期の入金
  （最古約定の直前 = 口座利用開始とみられる）まで遡及を確認。withdrawal_history も
  `--end` 逆方向ページングが機能。
  **ただしこれは検証口座での結果**であり、API 一般の遡及上限を確認したものではない
  （公式 docs に保持期間の記載はなく、より古い口座で打切りが起きないことは未確認）。
  「口座利用開始以来の全履歴が取れる」と一般化しないこと。
  なお **Web CSV フォールバックが不要という結論は撤回**した（実機確認 #7）。
  販売所取引は API に現れないため、CSV は取込の必須経路である
- **#2 信用取引レコード（2026-07-23 確認・クリア）**: eth_jpy の小口ロング 1 往復
  （1 日超保有・JST 0 時を 1 回またぎ）を実機で作成し、全レコードを検算一致まで解読。
  **以下の実測値は特定性を下げるため関係式に置換した**（値を丸めると恒等式の検算が
  合わなくなり、かえって証拠価値が失われるため）:
  - **判別**: trade / order とも信用は `position_side` が入る（現物はキー自体が欠落）。
    決済レコードは `side: sell` + `position_side: long`
  - **手数料**: 建て時は `fee_amount_quote: 0` のまま `fee_occurred_amount_quote` に
    発生額のみ記録され、建玉の `unrealized_fee_amount` に累積。決済時に建て分+決済分を
    合算して決済レコードの `fee_amount_quote` で一括精算
    （実測で `建て分 + 決済分 = 決済レコードの fee_amount_quote` が成立）
  - **建玉金利**: 0.04%/日を JST 0 時時点の建玉に課金（建て直後は 0、0 時またぎで 1 日分、
    24h 経過時点では増えない）。公式の信用取引ルールと一致。決済レコードの `interest` に
    原精度で精算（実測で `interest = product × 0.0004 × またいだ 0 時の回数` が成立）
  - **`profit_loss` は値幅損益から全手数料・金利を控除したネット実現損益**
    （検算: `profit_loss = 値幅損益 − Σfee − interest` が原精度で完全一致）。
    **段階 3 で fee / interest を再控除すると二重計上になる**（最重要）。
    信用の実現損益は決済レコードの `profit_loss` をそのまま採用する
  - **端数**: positions は 3 桁丸め表示、trade の fee 系は 4 桁四捨五入、
    `profit_loss` / `interest` は原精度。段階 3 は API 値を採用し、自前計算は検算
    （`interest = product × 0.0004 × またいだ 0 時の回数` 等）に限る
  - 2025-06-30 まで建玉金利 0 円キャンペーンがあったため、**2025 年分データの
    `interest: 0` は正常**（検証で異常と誤判定しない）
  - 補足: 注文照会は pair × order_id の複合キー（不一致は 50009）。
    `agents/error-catalog.json` の 50009 の記述に反映済み（Week 2 ⑤）
- **#3 手数料（2026-07-23 確認・クリア）**: maker リベート（マイナス手数料）が実在
  （btc_jpy の全約定——数百件規模——のうち maker が十数件、そのほぼ全てが負の
  `fee_amount_quote`）。
  **段階 3 は負の手数料を扱える設計が必須**（所得区分・計上方法は税制調査項目 2）。
  base 通貨建て手数料は 0 件（実測上、手数料は quote/JPY 側のみ）。現物では
  `fee_amount_quote` = `fee_occurred_amount_quote` が全件一致（docs 記述を全量追認）
- **#4 取引ペア（2026-07-23 確認）**: 検証口座の取引歴は十数ペア・全て `_jpy` 建て
  → 円換算ロジックはこの口座の検証では不要。`matic_jpy` / `rndr_jpy` の履歴が残存
  → **リネーム資産（MATIC→POL、RNDR→RENDER 等）の取得原価引継ぎマッピング**が
  新規論点（仕様検討事項）。**追確認（2026-07-24）**: `/spot/pairs` は BTC 建て 15 ペア
  （xrp/eth/ltc/bcc/mona/xlm/qtum/bat/omg/xym/link/mkr/boba/enj/matic の各 `_btc`）を
  返すが、**BTC 建てペアは新規注文停止（bitbank 社内確認では「delist 済み」）**。
  pairs はペア定義マスタとして停止済みエントリを保持し、取引可否は `is_enabled` /
  `stop_order` 系フラグで表現される。**フラグ実値は確定**（[tax-research.md](tax-research.md)
  付録E.5）: BTC 建て 15 組は `is_enabled=true` かつ `stop_order=true`（定義は有効なまま
  新規注文のみ停止）。したがって現行取引可否の判定に `is_enabled` 単独は使えない。含意:
  - 現行取引に BTC 建ては発生しない → 円換算（税制調査 §6・P-07）と暗号資産建て手数料
    （P-11）は「当年データ」の要件ではなく、**過去年からの簿価再構築**（前年末残高を
    持たない初回利用ユーザーが過去履歴を遡って取得価額を計算するケース）の要件として残る
  - Week 2 の全ペア横断取得は delist 込みの pairs マスタを回す（過去履歴の網羅に必要）。
    ここでは**取引可否で絞り込まない**（停止済みペアにも過去の約定履歴があるため）
  - 現行取引可否を判定する用途では `is_enabled && !stop_order` 相当を使う。
    上記のとおり `is_enabled` 単独では BTC 建て 15 組を「取引可」と誤判定する
  - BTC 建て約定レコードの実形状は新規約定では作れないため、過去に BTC 建て取引歴の
    ある口座のデータ提供（ヒアリング協力者・社内）で確認する
- **#5 出金 fee（2026-07-23 確認）**: crypto 出金は `amount` と `fee` が別建てで、
  **両者の合計がちょうど切りの良い額**になることから総引落 = amount + fee と推定
  （値は特定性を下げるため省略）。正規化では fee を
  別フィールドで維持。**crypto 建て出金手数料は暗号資産での支払いのため、それ自体が
  譲渡（課税イベント）になり得る** → 税制調査項目 2 の回答を待って段階 3 の扱いを決定
- **#6 データ量（2026-07-23 確認）**: btc_jpy 全期間で数百約定（5 年超）。
  個人規模の検証ではページング・性能問題なし。VIP/MM 規模はヒアリングで確認
- **#7 販売所（即時売買）は API に存在しない（2026-07-25 確認・仕様変更）**:
  `/user/spot/trade_history` が返すのは**取引所（板）取引のみ**で、販売所取引は
  注文 ID 照合で交差ゼロ。販売所は **UI CSV「売買履歴」でのみ取得可能**。
  → **UI CSV 取込が P1 から P0 へ昇格**（[tax-requirements.md](tax-requirements.md) §2.2 / §2.4）。
  これは残高突合（ガード(d)）が取込漏れを検出した実例でもあり、当初「積立」「ダスト消滅」と
  診断していた残差はすべて販売所取引だった（[tax-evidence/BALANCE_RECONCILIATION.md](tax-evidence/BALANCE_RECONCILIATION.md) 訂正履歴）
- **#8 年間取引報告書（現物）の列構成と恒等式（2026-07-26 確認）**: 実口座の年間取引報告書
  CSV を解析した。**値は持ち込まず、列構成と関係式だけを記録する**（丸めると恒等式の
  検算が合わなくなり証拠価値が失われるため、値そのものを書かない方針を採る）:
  - 符号化は **UTF-8 BOM 付き**。1 行目は氏名・発行者のメタ行で、ヘッダは 2 行目。
    → パーサはヘッダを**列名で探す**（1 行目を捨てる位置指定にすると様式変更で静かに壊れる）
  - 列は 17 本: 通貨名 / 年始数量 / JPY建て年中購入数量・購入金額 / BTC建て年中購入数量・購入金額 /
    JPY建て年中売却数量・売却金額 / BTC建て年中売却数量・売却金額 / 移入数量 / 移出数量 /
    支払手数料 / 貸出数量 / 返却数量 / 貸出損益 / 年末数量
  - **恒等式 R1（行内）**: `年末数量 = 年始数量 + 年中購入数量 − 年中売却数量 + 移入数量
    − 移出数量 − 支払手数料`。活動のある全行で厳密に成立。
    → **移出数量は手数料を含まない**（総引落 = 移出数量 + 支払手数料）。実機確認 #5 の推定と整合
  - **恒等式 R2（行間）**: `JPY 行の年中購入金額 = Σ(暗号資産行の年中売却金額)` および
    `JPY 行の年中売却金額 = Σ(暗号資産行の年中購入金額)`。厳密に成立。
    → 金額列は**グロス**（手数料控除前）で、JPY 行は暗号資産行の鏡像
  - **未確定事項#1（⑩支払手数料の丸め）への含意**: 支払手数料の列は API の
    `fee_amount_quote`（小数第 4 位丸め）より**多い桁数を持つ**。4 桁値の有限和は
    5 桁目を持てないので、**報告書は丸め前合計である可能性が高い**。ただし
    **観測は 1 口座のみで取引所への確認は取れていない**ため、既定（P-16: API 値を正）は
    変更しない。`tax verify-report` は差が「件数 × 半 ulp」以内なら丸め差と診断する。
    → 要求仕様 §9 未確定事項#1 の担当（開発／取引所）へ確認を回す
  - **BTC 建て列と貸出列が様式に存在する**（当該口座は全ゼロ）。BTC 建てペアは delist 済み
    （#4）なので当年データには出ないが過去年の再構築では出得る。貸出（貸暗号資産）は
    v2 §7 が「データソースが無い」としていたが、**年間取引報告書には年間合計が載る**
    → 貸出ユーザーへの経路が 1 本増える（実装は P2）
  - **年始数量はあるが年始「金額」は無い**。繰越簿価の代わりにはならないので、
    ガード(c)（前年繰越の確定）は引き続き必要

- **#9 販売所「売買履歴」CSV の様式（2026-07-26 確認）**: 実口座の CSV を解析。
  **値は持ち込まず列構成と性質だけを記録する**:
  - 列は 6 本: `注文ID / 通貨 / 売/買 / 数量 / 指値価格 / 売買日時`。**1 行目がそのまま
    ヘッダ**（年間取引報告書と違いメタ行が無い）。並びは新しい順で、年をまたぐ全履歴が出る
  - **手数料列が無い**（スプレッド内包）。付録E.3 のとおり。fee=0 ではなく列そのものが無い
  - **ペア列が無い**。通貨（base）だけで、クォートは JPY 固定として読むほかない
  - **約定代金の列が無い**。P-15 のとおり `数量 × 指値価格` で算出する。ただし
    **数量は 8 桁で丸められている**ため、この積は実際の約定代金と厳密には一致しない
    可能性がある（円建て注文なら代金側が丸い額のはず）。**未確定**: 正しい約定代金を
    CSV から復元できるか。差の大きさは `tax verify-report` が測る
  - **日時にタイムゾーン表記が無い**（`YYYY/M/D HH:MM:SS`）。JST 固定として読む。
    UTC として読むと年またぎの約定が前年分に落ちる（`jstDateTimeToMs`）
  - 重複排除キーは **注文ID**。取引所約定の `trade_id` とは別空間だが、`order_id` との
    交差は防御的に検査する（要求仕様 §2.4）
  - **「売買履歴」画面には 売買 / 定期購入 の 2 タブがあり、CSV ダウンロードは画面共通**。
    定期購入タブの列は `定期購入結果 / 注文ID / コイン / 数量 / 価格 / 注文日時` で
    売買タブと異なる。**定期購入も販売所なので API には現れない**（積立ユーザーの
    取込経路はここだけ）。取り違えて渡されたときに「タブが違う」と分かるよう
    `定期購入結果` 列で先に見分ける。
    **未対応・実データ待ち**: CSV 上の列名と `定期購入結果` の値域（成功 / 失敗など）が
    未確認で、失敗した注文を取り込むと取得価額が狂う。サンプルが手に入り次第サポートする

## 実データ検証（2026-07-27・検証アンカー 1 の初回実施）

実口座に対して `tax reconcile` / `tax verify-report` を実行した。**値は持ち込まず、
一致・不一致の関係と性質のみを記録する**。

### 結果

- **販売所 CSV の取込で残高突合が閉じた**。btc の残差は `--brokerage-csv` 投入で
  **厳密にゼロ**になり、投入前の残差が売買履歴 CSV の当年買付数量の合計と桁まで一致した
- ダスト銘柄のうち 2 銘柄は厳密ゼロ、残る 3 銘柄は **1e-9 オーダー**まで縮んだ。
  これは CSV の数量表示が 8 桁で、実約定が 9 桁目を持つことによる丸めで、
  v2 付録E.3 の「残りも CSV の表示桁による丸め（1e-9 オーダー）で説明できた」を独立に再現している
- **年間取引報告書（現物）との突合は全項目が許容幅内で一致**。うち JPY の支払手数料を除く
  全項目は**差が厳密にゼロ**。R1 / R2 も全行 ok
- 販売所を含まない年での突合だったため、これは **API 経路だけの完全な検証**にあたる

### 未確定事項#1（⑩支払手数料の丸め基準）への決定的な材料

唯一ゼロにならなかった JPY の支払手数料について:

- 報告書の値は API の `fee_amount_quote`（小数第 4 位丸め）より**多い桁数**を持つ。
  4 桁値の有限和は 5 桁目を持てないので、**報告書は 4 桁丸め値の合計ではない**
- 差は **件数 × 半 ulp（0.5×10^-4）以内**に収まった。つまり差は
  「1 件ずつ 4 桁に丸めたこと」だけで完全に説明できる

両者を合わせると、**報告書は丸め前の合計**であると結論できる。取引所への確認は
引き続き必要だが、既定（P-16: API 値を正）を見直す判断材料としては十分。

### 未確定事項#8（未観測データ形状）の 1 つを実観測

保留リストに 1 件だけ残った行が **`status=CANCELED` の入出庫**だった。要求仕様 §9
未確定事項#8 が「未観測」として挙げていた 4 形状（ショート建玉 / 部分決済 / fiat 入庫行 /
CANCELED の crypto 出庫）のうちの 1 つにあたる。

**防御実装は正しく効いていた**。CANCELED は成立していないので残高にも税務にも載せず、
その結果として全資産の突合が閾値内に収まっている。載せていれば残差が出ていた。

ただし保留の文言が「取り込めなかった」と読める形だったため、**正常な除外なのに異常に
見える**問題があった（種別も書かれておらず、入庫か出庫かも分からなかった）。文言を
「成立していないので載せません（異常ではありません）」へ改め、種別を明記した。

### この検証で見つかった実装の穴（修正済み）

1. **ダスト閾値が全通貨一律 1e-4** だった。JPY の 1e-4 は「100 分の 1 銭」で、
   約定代金の丸め由来の残差を毎回「未取込の処分」と誤診する。通貨別既定（JPY は 1 円）を入れた
2. **`reconcile` が pending の件数しか出していなかった**。理由が見えないと動きようがないので
   理由ごと出すようにした
3. **年分の取り違えを検出できなかった**。報告書 CSV は年度情報を持たないため、
   初回の実行で前年の報告書を当年として突合し、ほぼ全項目が不一致になった。
   不一致の割合が高いときに真っ先に年分を疑わせる警告と、ヒントへの候補追加を行った

## 社内資料からの確定事項: 信用の年間取引報告書（2026-07-26 受領）

信用取引の年間取引報告書の仕様書（社内設計資料・2024-11）を受領した。**現物とは別ファイル・
別様式**で、ペア（通貨）単位に 5 列を持つ: 通貨名 / 年末保有中売建玉 / 年末保有中買建玉 /
年中信用取引損益（円）/ 支払手数料（円）。ヘッダ（氏名・発行者）は現物と共通。

- **損益は個別法（FIFO）・約定ベース**。2024-11-26 の国税庁への照会で「計上時点の問題も
  含めて全て約定をベースに考える」との回答を得ている。現物の総平均法・移動平均法とは
  別系統（v2 §5 / FAQ 2-13 と整合）
- **年中信用取引損益 = 値幅損益 − 利息**。**取引手数料は控除しない**。手数料は
  「支払手数料」列に分けて載り、申告時にユーザーが現物の取引手数料と合算して
  国税庁計算書の「手数料等」欄へ入れる（取引手数料は消費税の課税対象という整理）
- **年末建玉は法人向け**（みなし決済損益額。FAQ 3-1-13）。個人の申告には不要で、
  保有中建玉の評価（未実現損益）には言及しない方針
- 桁は小数点以下 8 桁・四捨五入。信用取引の開始日は 2024-11-11

### P-06 への含意（受領仕様との矛盾の報告）

[tax-research.md](tax-research.md) v2 §5-4（P-06）は「年間取引報告書の⑨損益合計と
**定義・対象期間が一致し**、未決済建玉の評価損益や現物損益が混入していないことを
ツールが保証できる場合に限り、計算書互換出力ではネット額（差益/差損）を使用できる」と
条件付きで定めている。受領資料により、**この条件は満たされない**ことが判明した:

| | 定義 |
|---|---|
| 報告書「年中信用取引損益」 | 値幅損益 − 利息 |
| API `profit_loss` | 値幅損益 − Σ手数料 − 利息（実機確認 #2 で原精度の検算一致） |

したがって **報告書の損益 = `profit_loss` + Σ手数料** であり、`profit_loss` をそのまま
差益/差損欄に置くと報告書と手数料ぶんずれる。さらに、その手数料は計算書のどの欄にも
現れなくなる（現物の手数料と足せない）。

実装は手数料を**足し戻して**差益/差損に、手数料は必要経費（手数料等）に分ける形へ
変更した（`cli/tax/ledger/margin-entries.ts`）。**所得の合計は変わらない**
（収入 − 経費は同値）が、報告書・計算書との行の対応が変わる。

**P-06 の【方針】そのものは変更していない**（条件の当てはめが変わっただけ）。
受領仕様（tax-research.md）は実装側で書き換えず、本書に記録している。★監修時に
「ネット額不可・分解必須」で確定させる材料として添える。

なお「fee / interest を再控除しない」という規律（実機確認 #2 の最重要事項）は維持している。
実装がやっているのは控除の**取り消し**であって、二重控除ではない。

### 未解決（実データ突合で決める）

- 報告書の「支払手数料」が**精算ベース**（決済時に建て分と合算）か**発生ベース**
  （各約定日）かは資料から確定できない。年をまたぐ建玉があると両者はずれる。
  `tax verify-report --margin-csv` は `margin_fee`（精算）と `margin_fee_occurred`（発生）の
  両方を出し、どちらが一致したかで基準が判明する設計にした
- 報告書は生約定から FIFO を再計算する。取引所が付けた `profit_loss` と建玉の対応付けが
  一致するかは実データ突合で確認する

## 免責の修正: 「単一取引所だから計算できない」という言い切り（2026-07-27）

POSITIONING が「単一取引所のデータのみからは正確な譲渡原価を**原理的に**計算できません」と
無条件に述べていた。これは**誤り**で、しかも**自分のガードを否定していた**。

限界が生じるのは「単一取引所だから」ではなく「**口座外に同一銘柄の保有・取引があるとき**」。
bitbank だけで完結している銘柄なら、bitbank のデータが平均法のいう「全体」そのものなので
譲渡原価は正しく出る。まさにそれを識別するために v2 §1.2 の表示ガード (a)
アテステーション（`--attest` =「この銘柄を bitbank 口座の外で保有・売買していない」）が
存在する。無条件に否定すると、ガードを通した銘柄の数値まで無効に見え、
**bitbank だけで取引している利用者 —— 要求仕様 §1.2 の主ターゲットである B 層 —— を
蔑ろにする**文言になっていた。

v2 との齟齬ではない。v2 §1.2 がガードを定義している時点で計算が成立する条件を
認めており、**転記の過程で条件が落ちていた**という整理。文言を条件付きへ改め、
ガードが通った銘柄については数値が有効であることを述べる形にした。受領仕様
（[tax-research.md](tax-research.md)）は**書き換えていない**（P-06 と同じ扱い）。

なお呼称は **「税計算用参考データ」のまま**とする。一度「税務計算用データ」へ
変更したが差し戻した。「参考データ」単独だと品質への留保に読めるが、
**「税計算用」という修飾が付けば「税計算に使う参考資料」と読める**ため、
言い換える必要がない（製品判断・2026-07-27）。
