# 年間取引報告書（現物）との突合ガイド

`bitbank tax verify-report` が何と何を比べているかの参照資料。
**この文書に載っている数字は説明用の例で、実口座の値ではない。**

## 報告書の列と API の対応

| 報告書の列 | 突合キー | API 側の作り方 |
|---|---|---|
| 年始数量 | （比較しない） | 前年末残高。API からは当年ウィンドウで作れない |
| JPY建て年中購入数量 / 購入金額 | `buy_qty` / `buy_jpy` | 現物買約定の数量 / 約定代金 |
| JPY建て年中売却数量 / 売却金額 | `sell_qty` / `sell_jpy` | 現物売約定の数量 / 約定代金 |
| BTC建て年中購入・売却 | （比較しない） | 非 JPY クォート。CLI は P0 では計算しない → `unsupported` |
| 移入数量 | `deposit_qty` | 入庫（DONE のみ） |
| 移出数量 | `withdrawal_qty` | 出庫の `amount`。**手数料は含まない** |
| 支払手数料 | `fee` | 約定手数料 + 出庫手数料（当該通貨建て） |
| 貸出数量 / 返却数量 / 貸出損益 | （比較しない） | 貸暗号資産。API に相当データが無い → `unsupported` |
| 年末数量 | （比較しない） | 全履歴が要るので `bitbank tax reconcile` の担当 |

### JPY 行は暗号資産行の鏡像

暗号資産を売れば円が増えるので、報告書の JPY 行は次のようになる。

- JPY 行の「年中購入金額」= 暗号資産を売って**受け取った**円の合計
- JPY 行の「年中売却金額」= 暗号資産を買って**支払った**円の合計

したがって約定 1 件は base 側と quote 側の両方に計上される。
「BTC の買いが漏れている」ときは「JPY の売りも同額漏れる」ので、
差は必ず 2 か所に現れる。

## 突合の前に走る恒等式（`report_checks`）

報告書だけで閉じる関係式。API と比べる前にこれを検算して、
列の読み違い・行の欠落・編集済みファイルを弾く。

- **R1（行内）**
  `年末数量 = 年始数量 + 年中購入数量 − 年中売却数量 + 移入数量 − 移出数量 − 支払手数料`
- **R2（行間）**
  `JPY 行の年中購入金額 = Σ(暗号資産行の年中売却金額)`
  `JPY 行の年中売却金額 = Σ(暗号資産行の年中購入金額)`

いずれも実口座の報告書で成立を確認しているが、**取引所から確定仕様として
受領したものではない**。不成立はエラーにせず報告に留める。

## 差の診断

| diagnosis | 判定条件 | 典型的な原因 |
|---|---|---|
| `MATCH` | \|差\| ≤ 1e-4 | — |
| `FEE_ROUNDING` | 手数料で \|差\| ≤ 件数 × 5e-5 | API の手数料は小数第 4 位丸め値。報告書は丸め前合計の可能性が高い |
| `REPORT_EXCESS` | 報告書 > API | **販売所（即時売買）**。API に一切現れない。ほかに取込の打ち切り |
| `API_EXCESS` | API > 報告書 | 年分判定（JST）のズレ、重複排除の失敗、報告書の対象外（信用は別様式） |

### 手数料の許容幅を件数比例にする理由

API の手数料は 1 件ごとに小数第 4 位へ丸められている。報告書が丸め前合計なら、
差は最大でも「件数 × 半 ulp（5e-5）」までしか開かない。固定閾値にすると、
件数が増えるほど正常な丸め差を「取込漏れ」と誤診してしまう。

## よくある質問

**Q. 差がゼロにならない。バグ？**
販売所を使っていれば購入・売却に差が残るのが正常。差の量が
「まだ取り込めていない販売所取引の規模」を表している。

**Q. 信用取引はどこ？**
現物の年間取引報告書には現れない（別様式）。`verify-report` は信用イベントを
集計から除外し、除外件数を `warnings` に出す。

**Q. 年末数量が合っているか見たい**
`verify-report` は当年フローだけを見る。残高は全履歴が必要なので
`bitbank tax reconcile` を使う。
